# source-locations

Gold task on `cueforge` (repo `Bfa8uKesz2L9eeQTgZiC`, base
`474ce0944456bafbaa719a5e2304d56eaeccd768`, environment v1
`gold-repo-cue-forge-bfa8uk:v1`). Category `feature_request`.

## What the task is

`Finding.source` and `SourceRef` are public at the base, `docs/determinism.md`
orders findings by source path, line and column, the rehearsal JSON already
prints `source`, and no producer ever fills it. `source_map.ref_for` and
`normalize_source_path` have no callers, and the JSON loader cannot give a
position at all. The request: every load-time and compile-time finding
points at the authored node it is about (file relative to the workspace
root, 1-based line and column of the node's first character), YAML and JSON
alike, through multi-file workspaces; assertions are checked when compiling
so their findings have a node to point at; `compile --format json` prints
`source`; rehearsal output and every digest stay byte-identical.

Where the difficulty sits: nothing at the base prints a position, so a solver
has no oracle and every rule is a place to slip -- key versus value versus
mapping start, 1-based columns counted in characters after JSON escapes, the
merged `cues[3]` living in the second source file, the repeated-key rule, and
the trap that positions must never enter a digest (a comment line moves every
`line`, and `docs/determinism.md` says comments are not semantic).

## How the tests are written

Every case builds a production as text in `tmp_path`, loads it through
`load_production`, compiles through `compile_production`, and reads
`finding.source.path/line/column` -- base API only. Expected positions are
derived from the fixture text (`at(text, line, token)` finds the token's
column), never from running the implementation. Where the request promises a
CLI object, the case drives `cueforge.cli.main.app` and reads the `source`
key. The one wording assertion (`CHANGELOG.md` mentions "source") is what the
instruction asks for.

## The lever (round 4)

Rounds 2 and 3 showed the strong calibration model solving every stated
behaviour (58/59 in all eight trials, blocked only by an ambiguous null).
The difficulty now sits in YAML anchors and aliases, where PyYAML's own
marks are the wrong answer twice over: an anchored node's `start_mark` is
the `&`, and an aliased node is the very same object as its anchor. The
instruction states both rules in one sentence (an anchor names its node,
which opens after it; a node reached through an alias, with everything
inside it, points at that `*alias`, the outermost when aliases nest). The
reference hooks `compose_node` to keep the alias site on a shallow clone,
carries it down the walk, and moves an anchored node's mark past its
properties. `tests/locations/test_yaml_aliases.py` holds the eight cases (f2p 66 in all);
`mutants.py` carries five wrong readings of the rule plus the null-source
one.

## What the verifier does

Runs from the frozen frame; only the RUN TESTS block is ours. Before any
suite: restore every `frozen_files` path from the base commit (base tests,
`test_lab/`, `examples/`, `pyproject.toml`), remove `protected_absent` names
and any module shadowing the framework or the standard library at `/app` or
`/app/src`, then let git say whether every restored path matches the base
commit (`git diff --name-only <base> -- ...`) and check the held-out pins by
digest. The sha256 pins on `frozen_files` are consulted only when git cannot
be asked: they were taken from the snapshot export, whose `pyproject.toml`
carries redacted metadata, and the platform's base commit does not (round 1
failed oracle_nop on exactly that line). Each suite runs under `python3 -I` with the
framework bound before `/app/src` goes on the path; the runner checks where
pytest came from, tallies outcomes in-process, writes the report only into
scratch and signs it with a token it read from stdin before anything under
`/app` could load. The shell ends the runner's session and sweeps every
process that was not alive before the suites, then publishes a report only
if its signature matches; every refusal publishes all declared ids as failed
so the grader always has a report. `grader.py` is the canonical shared file.

Residual, measured: a forger willing to walk interpreter frames from inside
the runner process could read the token; nothing in-process closes that.
